# 设计说明

这份文档记录**代码里那些"为什么这么写"的决定**。README 讲怎么跑起来，这份讲为什么长成这样。

代码注释里凡是写「见设计文档」的地方，指的都是这里。改动设计时请同步更新本文件——一份和代码对不上的设计文档，比没有更糟。

---

## 分层：`core/` 与 `game/`

这是本项目最重要的结构约束。

`core/` 放的是**任何一款弹幕射击游戏都会需要**的东西：二维向量、圆形碰撞检测、精灵动画表、固定步长主循环、整数倍缩放、输入值对象、资源路径解析。它**不 import 任何和东方有关的概念**——在 `core/` 的代码里找不到"自机""残机""符卡"这些词。

`game/` 才知道自己在做东方：自机、敌机、BOSS、子弹、道具、擦弹、炸弹，以及读关卡文件、跑 BOSS 脚本的逻辑。

分成两层有两个实际好处：

1. `core/` 的数学和碰撞可以**完全不启动显示设备**就被测试。`tests/` 能快速跑起来，靠的就是这条边界。
2. 改弹幕的运动学算法时，改动范围清晰，不会一不小心碰坏界面代码。

这条边界由 `tests/testProjectLayout.py` 用 AST 扫描守着——它检查 `core/` 下的模块有没有 import `touhou.game`，包括绝对导入、相对导入（`from ..game import ...`）和 `from touhou import game` 三种形态。

## 关键接口约定

三条贯穿全项目的约定。它们**错了不会崩，只会让画面整体不对**，所以由测试锁死。

### 一、角度：0° 指向正上方，顺时针增大

```
0° → 正上      90° → 正右      180° → 正下      270° → 正左
```

即 `Vector2.fromDeg(0) == (0, -1)`，`rotateDeg(90)` 把「正上」转成「正右」。

**为什么是这个约定**：屏幕坐标系 y 轴向下，标准的旋转矩阵 `[[cos,-sin],[sin,cos]]` 在这个坐标系里看起来本就是顺时针。所以 `rotateDeg` 就是一次普通矩阵乘法，不需要任何符号翻转，写和读都直白。写自机狙和环形弹幕时，`0°` 就是朝上打、`90°` 就是朝右打，不用在脑子里换算。

**⚠️ 移植警告**：参考项目 NumPix/pygame-touhou 的旋转方向与此**相反**。它的 `Vector2.rotate` 写的是 `np.matmul(self.coords, rotor)`——**行向量乘矩阵**，数学上等价于旋转了**负**角度，所以它的「正上转 90°」得到的是「正左」。

从它的关卡数据移植角度值时**必须取负**：

```python
ourAngle = (-referenceAngle) % 360
```

不处理的话，所有定向弹幕（自机狙、扇形、锥形）会整体左右镜像。这不是崩溃，是"跑得起来但打向错误方向"——比崩溃难查得多。

**⚠️ 移植警告（第二处）：它的自机狙角度本身算错了**

它用 `Vector2.angle_between` 算瞄准，而那个函数是 `arccos(dot/(|a||b|))`——点积反余弦的值域只有 `[0°, 180°]`，等于**丢掉了「目标在源点上方还是下方」这一半信息**。

实测（把它的公式原样搬过来跑）：自机位于敌人**上方**时，正上被算成正下、右上算成右下、左上算成左下——整体**垂直镜像**。

**这个 bug 骗过了所有人，原因值得记住**：arccos 写法在**下半屏（90°–270°）完全正确**，只在**上半屏**出错（72 个采样方向里错 35 个，全部在上半屏）。而敌人从游戏区上沿开火、自机被钳制在游戏区里，自机**永远在敌人下方**——瞄准角恒在下半屏。所以它自带的关卡看着一直是对的。

推论很硬：**「敌人打自机」这种端到端测试永远抓不到它**，写多少遍都没用。只有在纯数学层、让目标出现在上半屏的测试才有用。这也是为什么这条回归测试放在 `tests/core/testVector2.py` 而不是别处。

要移植的是**意图**（朝自机打），不是那个公式。本项目直接写：

```python
aimAngleDeg = (player.position - enemy.position).angleDeg()
```

`Vector2.angleDeg` 走 `atan2`，值域是满圆 `[0°, 360°)`，八个方位都正确。回归测试见 `testAimingAtATargetPointsAtItFromEveryDirection`。

**⚠️ 移植警告（第三处）：攻击参数的时间单位不是秒**

它攻击参数里的 `start_time` 与 `delay` 是**敌人轨迹的 `t` 单位**，不是秒——它的 `Enemy.move` 里推进的是 `self.t += self.speed * delta_time`，而 `speed` 是敌人轨迹速度。只有轨迹 `speed` 为 1 时两者才恰好相等；弹刺球那类 `speed` 2.4 的敌人，写 `0.75` 的间隔实际是 0.31 秒。

**换算方向是「除以」敌人速度，不是乘**：`t` 每秒前进 `speed` 个区间，所以
`秒 = t 值 / speed`（`0.75 / 2.4 = 0.31`）。写成乘会让每个间隔长 `speed²` 倍——
对 2.4 的敌人是 5.76 倍，**结果是 98 组攻击全部在敌机离场后才开火**，
而那正是本节要防的失败模式。

> 这条换算方向在本文件里一度写反过（写成了「乘」）。发现它的办法是拿它去
> **验算 122 组真实攻击**：按 `u` 单位算，没有一组在敌机离场后开火；
> 按「秒」算，98 组越界。数字对不上就是方向错了。

### 二、相切不算碰撞

`Collider.checkCollision` 在距离恰好等于半径和时返回 `False`（用严格小于号）。弹幕游戏里边缘擦过不该算命中。

### 三、零向量归一化返回零向量

`Vector2.zero().normalize()` 返回 `(0, 0)` 而非 `NaN`。自机没有按方向键时方向向量就是零向量，这个守卫是必须的——没有它，松手就会得到 `NaN` 坐标。

## 主循环：固定步长

**逻辑恒以 1/60 秒一步推进，与真实帧率解耦。**

本项目不使用变步长（`position += velocity * deltaTime`）。原因不是性能，是正确性：

弹幕游戏的一切都建立在「第 N 帧」这个概念上。变步长下，一台机器上子弹飞得快一点、另一台上慢一点；帧率抖动时，一颗高速子弹可能某一帧直接跨过自机的 2px 判定点——**穿透**，玩家会莫名其妙地死。而且录像回放、逐帧调试、数值平衡全都无法进行，因为同一份输入不再产生同一个结果。

采用累积器模式，实现在 `core/gameLoop.py`：

```
累加真实经过时间 → 每满一步就跑一次逻辑 → 渲染一次（与跑了几步无关）
```

**卡顿时丢弃积压，而非逐帧追赶。** 设了单帧最大步数上限，超出部分整段丢弃。保留积压的话，接下来每一帧都会再次触顶，游戏会长时间处于追赶状态，表现为持续慢动作——这比"卡一下"糟糕得多。

这个类**刻意不 import pygame**，因此它的全部行为都能被穷尽测试。

## 输入：轮询与事件的取舍

移动与射击要的是「这一帧按住没有」——轮询键盘状态（`pygame.key.get_pressed()`）。暂停与菜单要的是「刚刚按下了」——用事件。两者用途不同，不混用。

所有输入收敛成不可变的 `FrameInput`（frozen dataclass），人工输入与将来的 AI / 录像回放走同一条路径，逻辑层无需区分二者。键盘状态通过一个只要求 `__getitem__` 的协议（`KeyState`）传入，所以翻译函数可以脱离 pygame 单独测试。

### 必须关掉 SDL 的文本输入通道

`Game.__init__` 在 `set_mode` 之后调用 `pygame.key.stop_text_input()`，**这一行不能删**。

pygame 建窗口时**默认开启**文本输入，于是中文输入法对游戏窗口生效。玩家一旦按下
任意字母键（比如 A），`pygame.key.get_pressed()` 就**不再上报任何按键状态**——
表现为「按了 A 之后方向键全部失灵」，把输入法切到英文或按住 Shift 就恢复。

这个 bug 有三个特点，合起来说明为什么值得专门写一段：

1. **在没有输入法的机器上完全复现不出来**——英文环境、或者输入法关着，一切正常。
2. **不崩、不报错**，只是输入整体失灵，很容易被当成「游戏卡了」。
3. **靠读输入代码查不出来**：读的是 8 个固定键常量，没有任何代码路径能让一个
   未映射的键影响其他键。机制在 SDL 层，不在我们这边。

将来做记分板之类需要输入文字的地方，按需 `start_text_input()` 并在用完后再关掉。
`tests/testMain.py` 里有一条测试盯着这次调用——它守的正是「多数机器上复现不出来」
这个性质。

## 渲染：逻辑分辨率与整数倍缩放

逻辑分辨率固定 **640×480**，游戏区 **384×448**，位于 `(32, 16)`；右侧 224px 是 HUD 区。与原作布局一致。

每帧先渲染到一张 640×480 的离屏画布，最后**一次性整数倍缩放**到窗口。倍率不写死——启动时选**能塞进显示器的最大整数倍**，所以常见分辨率下是 ×2 或 ×3，4K 屏上会是 ×4。（`chooseScaleFactor` 只设了下限 1，没有上限。）

**坚持整数倍的理由**：非整数缩放会让像素变成大小不一的矩形，画面看起来像蒙了一层脏东西。宁可留黑边。

两处缩放用的是**不同**的插值方式，这是刻意的：

| 何处 | 方法 | 为什么 |
|------|------|--------|
| 窗口缩放（每帧） | `pygame.transform.scale`（最近邻） | 保住像素画的清晰边缘 |
| 背景预缩放（一次性） | `smoothscale` | 1200×800 → 384×448 是一次大幅缩小，最近邻会丢像素丢得很难看 |

## 子弹与弹幕场

一颗子弹 = 一个圆 + 一个速度 + 一张贴图（`game/entities/bullet.py`）；
成批的生成、推进、回收与绘制在 `game/bulletField.py`。

### 子弹继承 `Collider`，而不是组合一个

子弹**是**一个圆，所以 `bullet.checkCollision(player)`、`bullet.position.y`
都是自然写法。`Collider` 已带 `__slots__`，子类再声明自己的 `__slots__` 后
实例仍然没有 `__dict__`（实测），池化想要的效果不会丢。

**扩展一律走「加字段」，不要写 `Bullet` 的子类**：子类会牵出每类一个池、
子类 `__slots__` 纪律（漏写会把 `__dict__` **静默**加回来）、热循环里的
isinstance 判断；而加字段只是「一个 slot + `reset` 一行 + `update` 一行」。

### `angleDeg` 是存下来的，不每帧从速度反推

反推会把方向**算塌**。实测 `Vector2.fromDeg(θ, 0)` 对 θ = 0/45/90 全都给出
`(0.0, -0.0)`，而 `angleDeg()` 对它的返回值一律是 `0.0`——零速弹反推角度会
把这三个方向全变成「正上」，「停下再转向」这类弹型会因此画错方向。
（这不是零向量那个坑：零速弹的 `velocity` 并不是 `Vector2.zero()`。）

### 出屏回收必须带上速度方向，不能只判矩形

第一版写的是「跑出游戏区外扩 N 像素的矩形就回收」。这条规则**能用，但要多付一倍多的代价**。

把 `level_1.json` 的坐标换算到我们的游戏区之后（换算见「关卡数据与坐标系」一节），
敌人轨迹的控制点最远探到游戏区外 105px，而 **114 个敌人里有 105 个**至少有一个控制点
落在「游戏区外扩 32px」的回收矩形之外。它们的子弹诞生在回收矩形之外、却朝场内飞，
只按矩形判会在生成那一帧就被杀掉。

反过来，让矩形容得下这些子弹就需要 105px 余量——那会让回收矩形面积变成游戏区的
**2.3 倍**：子弹要飞出 105px 才回收，池占用与模拟量都白涨一倍多。

方向判定把两个问题一起解决：在边界上即回收，且永不误杀入场弹，代价同样是四次比较。
所以判的是「已经出场**并且**还在朝场外飞」。余量因此只剩一个职责——
**贴图占位**：子弹不能在自己还有像素落在游戏区内时被删掉，取值依据见 `constants.py`。

> ⚠️ **更正记录**：这一节原先写的是「敌人轨迹横跨 `x ∈ [-120, 720]`、114 个敌人里
> 有 57 个越过右边界、右侧余量要开到 304px、**没有任何一个余量值能同时满足两端**」。
> 那些数字是拿**未经坐标换算**的原始数据去比我们的游戏区算出来的，全部不成立；
> 「没有任何余量值能同时满足两端」也是错的——105px 就行。规则本身仍然更优，
> 只是赢得没那么戏剧化。留着这段记录是因为它恰好是本文件反复强调的那类错误：
> **不崩溃，只是数字整体偏了，而且看起来很有说服力。**

### 对象池

`BulletField` 独占 `active` 与 `free` 两个列表，池不单独成类：「一颗弹什么时候
被回收」完全由场决定，池的唯一调用方就是场；两个列表放在一起，「一颗弹恰好在
两者之一」这条不变量才只在一个地方可检查——而下面那三行正是它唯一会被写错的地方。

```python
dead = self.active[index]
self.active[index] = self.active[-1]
self.active.pop()  # 丢弃重复的末尾引用，它不是死者
self.free.append(dead)
```

写成 `self.free.append(self.active.pop())` 是**错的**：`pop()` 取的是末尾，而此时
末尾正是刚被复制进 `index` 的**幸存者**。后果是幸存者同时躺在 `active` 和 `free`
里（下一轮 `spawn` 把它再发一次，同一颗弹被推进、绘制、碰撞两遍），真正的死者泄漏。
**在「末尾那颗死」的场景下这个错误写法恰好是对的**——所以只有「中间那颗死」的
测试能抓到它，两种场景都必须测。

`__init__` 委托给 `reset`，两者不会漂移；`reset` 必须设满**每一个**字段，漏一个是
「新弹继承上一发的状态」，池化最经典的 bug。`reset` 只拷 `position` 的分量、不存
调用方传进来的那个 `Vector2`：弹幕模板必然会写 `spawn(spec, enemy.position, ...)`，
直接存引用的话敌人一移动，所有引用它的子弹会一起跳（实测三颗弹的 x 从 100 全变 140）。

### 关卡数据的 sprite 描述：第 4 个字段是判定半径，不是帧数

格式是 `[路径, 帧宽, 帧高, 判定半径, 偏移]`。第 4 个字段**容易误读成帧数**——
`kunai_0` 写 4、`ellipse_bullet_0` 写 6，看着就像「4 帧」「6 帧」，而这两张图分别是
16×16 和 24×24，根本切不出那么多帧。

判定依据是：**同一张 `ellipse_bullet_0.png` 在不同弹幕下分别写 4 和 6**。帧数不可能
对同一个文件取两个值，判定半径却正该如此——它是每套弹幕各自的参数，不是贴图的固有
属性。所以 `BulletSpec.radius` 必须是显式参数，不能从贴图尺寸推导。

帧数则是**从图片尺寸推出来的**（`SpriteSheet` 本来就是这么切的），数据里没有、
也不该有这个字段。

`rotatesToVelocity`（可选，缺省 `true`）决定这颗弹跟不跟着速度转。它逐弹种给，
不是全局开关：尖头弹（苦无）不转就歪，必须转；而**圆球转了看不出来**，给它 360 个
预旋转缓存条目纯是浪费——`gather.png` 里抠出来的大玉是 172×172，转一圈就是几十 MB
（缓存是每张表一份，键里含帧号）。所以大玉在数据里写着 `false`。

### 贴图的原生朝向就是 0°

有朝向的两张贴图（苦无、橄榄形弹）**在文件里本来就是朝正上画的**，正好等于本项目
「0° = 正上」的约定，所以 `getRotated(帧, angleDeg)` 直接就能对上，不需要任何偏移。

绘制必须用 `frame.get_rect(center=...)`：旋转后外接矩形会变大，按
`position - halfSize` 算会偏出 3px 以上。非直角角度有 pygame 整数取整带来的
≤1px 中心偏移——每颗弹角度固定，所以不会抖动，也不必修。

## 弹幕模板层

敌机打出去的弹幕长什么样，由 `game/patterns/` 决定；`EnemyField` 只负责
「什么时候、从哪、朝哪打」。

### 注册表：加模板不需要改加载器

规格 §7.3 定了形态：`PATTERN_REGISTRY: dict[str, Callable]` + `@registerPattern(name)`。
**但规格没写模板函数的签名**（`Callable` 没有参数化），本项目定为 `(params, context) -> None`。

本项目在规格之上**多登记了一样东西：参数类型**（`PATTERN_PARAMS`）。理由是没有它，
「加模板不改加载器」就是空话——加载器得知道每个模板的具名参数长什么样才能校验。
参数类的字段名与关卡数据里的名字一一对应，多一个少一个都会在加载时报错，
错误信息带位置（这是规格 §7.5 举的例子：`params.speed 应为数字，实际为字符串 "1"`）。

### `FiringContext`：参数是数据，上下文是环境

模板函数拿两样东西：`params` 说「打什么」，`context` 说「在哪打、朝哪打、用什么随机数」。
这条界线让模板能脱离 pygame 场景与敌人对象被单独测试，自机狙的退化情形
（自机与敌机重合）也只在调用方一处处理。

`context.volleyIndex` 是「这一发是第几波」：时序归调度方管、弹型只管打**一发**，
但环形弹的「第 n 环整体旋转 n × 角度」需要知道 n。

### 随机数必须注入

规格 §5.2：所有随机走注入的 `random.Random`，禁止全局 `random`。
理由是硬性的——`DESIGN.md` 把「同一份输入产生同一个结果」写成固定步长存在的意义，
用全局随机数会让录像回放与逐帧调试同时失效。参考项目的
`AttackFunctions.random()` 正是用全局 `random.randint`，**移植时改掉了**。

好处立刻兑现：随机弹型也能被确定性测试（同一个种子断言逐发精确的角度）。

### 三种弹型

| 弹型 | 形状 |
|------|------|
| `wide_cone` | 对称扇形：恰好 N 发，相邻夹角固定，可有正中一发（N 为奇数时） |
| `wide_ring` | 完整圆环，逐环整体旋转，累积成螺旋 |
| `long_random` | 每发各取随机方向 |

**自机狙不移植参考项目的公式**：它用 `acos`（点积反余弦）算，值域只有 `[0°, 180°]`，
自机在敌人上方时会垂直镜像——见「移植警告（第二处）」。我们用 `atan2` 的
`Vector2.angleDeg`，八方位都正确。

**螺旋方向**：`deltaAngleDeg` 的正负决定往哪边绕。参考项目的角度方向与我们相反
（移植警告一），所以迁移时把有符号角度**取过负**了——模板里别再翻一次。

## 自机：状态机、射击与炸弹

自机（`game/entities/player.py`）除了移动与立绘，还有**射击、炸弹、受击与残机**。

### 复用 `Bullet`，开第二个弹幕场

**自机子弹不另造一套实体**，直接用 `Bullet` + `BulletField`，只是换一个实例：

- `Bullet` 已经是「一个圆 + 速度 + 贴图 + 池化 + `__slots__`」，没有一处敌机专属逻辑；
- `BulletField` 是「容器 + 推进 + 回收 + 绘制」，同样没有；
- 自机子弹**不旋转**，`BulletSpec.rotatesToVelocity=False` 现成支持；
- 出屏回收同理——自机子弹朝上飞，飞出上边界即回收，方向判定规则正好适用。

两个场各一个实例（`Game.bulletField` 是敌弹、`Game.shots` 是自机子弹）：敌弹打自机、
自机子弹打敌机是两条不同的碰撞路径，共用一个列表只会互相干扰。

代价只有一处：`BulletSpec.damage` 这个字段**敌弹也用不上**（敌弹命中自机是「碰到即死」，
不分伤害）。留着它，比为了自机子弹再造一套实体（新类、新池、新绘制、两处 `isinstance`）
划算得多。

### 状态机

```
alive ──被弹命中──> dying（8 帧死亡炸弹窗口，不能动也不能射）
                     ├─ 窗口内按下 X 且还有炸弹 → 消耗一枚、清空敌弹、回复无敌 → alive
                     └─ 超时 → 【死亡冲击波】+ 残机 -1、雷补足
                                            → respawning（下方升起 + 180 帧无敌）→ alive
                                                                                        │
                                                                  残机已是 0 时再死 ──> dead
```

规格只点名了 `dying`，其余三态是本项目定的。几处规格没写、由本项目补上的：

- **`dying` 期间不能移动、不能开火**：被击中的那一刻就该定住。规格没写，但「已经
  死了还能动、还能打」会让人以为判定没生效。
- **无敌期间再中弹忽略，`dying` 期间再中弹也忽略**（窗口已经在跑）。
- **`respawning` 期间不可操作**，升起约 60 帧，之后恢复可操作但保持无敌到 180 帧用满。
  无敌期间**立绘闪烁**——否则「现在是不是无敌」肉眼完全看不出来，而刚复活、刚放完
  炸弹时玩家最需要知道的就是这件事。
- **残机是「剩余备命」，先判再减**：残机 0 时玩家**还在场上打**（那是最后一条命），
  再死一次才出局。所以 `START_LIVES = 8` 一共能死 9 次。写成「先减再判」的话，残机 1
  的死亡就直接出局，白少一条命——这个 bug 是玩家实测报上来的，`testTheLastSpareStillRespawns`
  守着它。
- **`START_LIVES` 目前刻意偏高（8）**：还没有难度选择，8 条命是给不会玩的人试弹幕用的
  （原作默认 3 条，靠选项里的「残机数」自己调）。难度选项落地时它应当变成难度表里的
  一项，而不是继续写死。
- **死亡补雷**：复活时若雷不足 `START_BOMBS` 枚就补足，**多了不动**（写成
  `self.bombs = START_BOMBS` 成了重置，将来有道具时会倒扣玩家的雷）。手感上的理由：
  后期弹幕越来越密，手里没雷就只能靠躲，一次死亡会变成不可逆的劣势。补的是**复活时**
  的库存，所以死亡炸弹不能靠它续命——那次消耗发生在死亡之前。
- **撞到敌机机体也是死**，判定用的是`bodyRadius`（比贴图略小），见「敌机身上有两个半径」。
- **死亡冲击波**：出特效、清空敌弹、全屏敌机掉一点血，三件事同帧发生。见下一节。
- **最后一条命也没了就不做 Game Over**：没有结算画面可去，所以只是停止复活，
  游戏继续跑（敌机照飞来）。结果画面落地时接上。
- **雷有伤害，而且比死亡冲击波高两个数量级**：`PLAYER_BOMB_DAMAGE = 38` 对
  `PLAYER_DEATH_DAMAGE = 1`。这不是随手调的数——关卡里的血量分布是 1/10/25/40，
  38 的含义是「一口气清掉所有小怪与普通精英，只有 40 血的顶级精英差一点打死」，
  而死亡冲击波只够清 1 血的小怪。定位上：死亡冲击波是白送的补偿，雷是消耗品，
  原作里它就是打 BOSS 的主要手段之一。
  两个伤害值**是两个独立的手感旋钮**，所以写成两条函数
  （`collision.playerDeathShockwave` / `collision.playerBombShockwave`）而不是
  一个带参数的函数——后者会让人以为这两个数该一起调。
- **雷的消弹 / 伤害 / 特效三件事同帧发生**，与死亡冲击波那条规矩一致：它们在
  `Player.useBomb` 里挨着三句，中间不插条件。**死亡炸弹救回来的那次也放这三样**
  ——它已经是一次货真价实的雷了；不发射的是**死亡**冲击波（那次没死，
  `die()` 根本没被调用，所以不扣残机、不补雷、不炸死亡特效）。
- **雷的特效暂时复用死亡那份扩散环**：雷还没有自己的美术，`main.py` 把同一份烘好的
  帧表传给 `bombEffectFrames`。传的是**同一份帧对象**而不是一个「共用开关」——
  等雷的素材到位，换一张烘好的表就行，`Player` 那边一行不用动。时长是独立的
  `BOMB_EFFECT_FRAMES`（现在与死亡同为 30 帧），会先于素材分家。

`Player` 继承 `Collider`，道理与 `Bullet`、`Enemy` 相同——自机**是**一个判定圆，
于是 `bulletField.hits(player)` 直接就能用。注意 `radius` 是**判定点半径**（2px），
而立绘半宽半高走 `halfSize()`，两者刻意不同：躲弹要精确，画面上看到的却是 25×50 的立绘。
判定点只在**低速（按住 Shift）**时画出来，规格 §6.2 要求如此。

### 按下 ≠ 按住：炸弹的边沿输入

炸弹要的是「**刚刚按下**」，而键盘轮询只会给「现在按着」。规格自己把这条界线划得很清楚
（暂停与菜单要的就是刚刚按下 → 用事件），但事件和固定步长循环结合有个真问题：

**一次渲染帧可能跑 0~5 次逻辑步**（`MAX_STEPS_PER_FRAME`，卡顿时还有丢弃）。把事件
直接填进当帧的 `FrameInput` 会两头出错：

- 一帧跑 3 步 → 同一次按键被当成 3 次 → **按一下 X 放出三个炸弹**；
- 一帧跑 0 步 → 按键被丢掉 → **死亡炸弹那 8 帧窗口里按 X 没反应**，而这正是它最要命的地方。

所以 `core/input.py` 里有一个 `PressLatch`：`handleEvents` 把 KEYDOWN 记成一笔
**计数**（不是布尔——一帧内确实可能按下两次），由**第一个真正执行的逻辑步**取走一个。
`consume()` **总是**覆盖 `bomb`，包括把它压回 False：传进来的轮询值若被当成边沿，
按住 X 不放会每帧放一个炸弹，几秒就能把库存放空。

### 死亡炸弹窗口

规格 §8.5 把边界钉死在帧数上：**第 8 帧按 X 存活、第 9 帧死亡**。实现是
`updateDying` 里两个 `return` 的先后顺序——`dyingFrames <= 0` 必须排在按键判断之前，
调换就会让第 9 帧的按键也生效。`tests/game/testPlayerState.py` 里有四条测试守着这个边界。

### 死亡冲击波：一个事件，三处表现

自机死亡时会做三件事，它们**必须同帧发生**：

| 表现 | 在哪 | 给谁 |
|------|------|------|
| 爆开的环形特效 | `effectField` + `entities/effect.py` | 给眼睛 |
| 清空全场敌弹 | `collision.playerDeathShockwave` | 给玩家的补偿 |
| 全屏敌机各掉一点血 | 同一个函数 | 给敌人的账 |

三件事分在三个模块里，但**调用点是相邻的两行**，都在 `Player.die()` 里——这就是
「同步」的实现方式：不各管各的计时，而是同一个瞬间的三个后果。中间插任何条件都会
让它们走散。

**冲击波在「最后一条命也没了」那一次同样发生**：那是死亡，只是不再复活。
**死亡炸弹救回来的那一次不发生**：那不是死亡（`die()` 根本没被调用），而炸弹自己
本来就清弹。写成「按下 X 就放冲击波」的话，玩家等于用一枚雷换来一次全屏清场 + 掉血，
雷就变成输出手段了。

**伤害值取 1**（`PLAYER_DEATH_DAMAGE`）：关卡里 114 架敌机有 98 架正好是 1 血，
所以它**刚好秒杀小怪**，对 10/25/40 血的精英只是掉一层皮。这是一条有上下界的规则
——伤害 0 秒不掉小怪，伤害 2 会连 2 血的也清掉（而血量的下一档直接跳到 10，
2~9 那一段本来就不该有东西被一击清掉）。测试把两侧都钉住了，且**用字面量而不是
引用常量**：引用常量的话，改常量时断言跟着一起变，等于什么都没测。

### 一次性动画

`Effect` 是「位置 + 一串烘好的帧 + 播放进度」，放完自己就没了；容器是
`EffectField`。它**不进对象池**——一场战斗里特效出现的次数就是死亡次数，个位数。

**帧是烘出来的**（`bakeExpandingRing`）：死亡特效的素材是一张 500×500 的**环形**
贴图（中空的一圈光晕），动画是「由小到大扩散 + 由亮到暗淡出」，而贴图只有一张。
每帧现算就是每帧 smoothscale 一张 500×500，三十帧下来是实打实的开销——尺寸与亮度
的序列是固定的，所以烘一次、放的时候只 blit。这与「按角度预旋转缓存」是同一个道理。

淡出走 `BLEND_RGBA_MULT`（把 alpha 通道乘一个系数），不用 `set_alpha`：后者作用在
带逐像素 alpha 的表面上时是「整体透明度」还是「覆盖逐像素 alpha」，各后端并不一致。

特效的**出生那帧不推进**，靠的是 `Game.update` 里 `effects.update()` 排在自机之前
——与子弹「出生那帧停在炮口」是同一条规矩。

### 射击

火力档位表（规格 §6.3）给出弹道数，再均分角度发射。规格**点名参考项目的实现有缺陷**
（`int(0.6 * power)` 让索引 3 永远取不到，且被两轮有损取整），所以不照搬原代码。
查表与角度都是**纯函数**（`laneCountForPower` / `shotAnglesDeg`），因此五个档位可以逐个测
——本轮没有道具，`power` 固定为 `POWER_START`，可达的档位只有一个。

相邻弹道的夹角规格**没给**，`PLAYER_SHOT_ANGLE_STEP_DEG` 是起点值，需要实测调整。

`shotCooldown` 是**倒计时**（还剩几帧才能开火，0 表示现在就能开），不是「已经攒了几帧」。
写成倒计时是为了让「松手时归零」自然地产出**按下的第一步就出弹**：攒帧数的话第一发要等满
6 帧（100ms），按下去到出弹有一段能感觉到的空白。

### 炸弹：两半缺一不可

规格 §6.5 强调「只有无敌没有清弹，玩家仍被弹幕困住；只有清弹没有无敌，按了等于白按」，
所以 `useBomb` 两件事一起做。无敌时长规格只说「一段无敌时间」，本项目取 180 帧与复活一致，
是起点值。

**清掉的敌弹不转化成道具**：道具系统还没有（星星、PoC 回收线、高度计分要一起做，
规格 §6.6 说这两件事「必须一起实现」）。等道具落地时在这里补上。

### 碰撞分两档

规格 §5.5 把碰撞分成两档，本项目的实现与它一致：

| 谁和谁 | 做法 | 在哪 |
|--------|------|------|
| 自机判定点 vs 敌弹 | **全量比较**（弹药基数不大） | `BulletField.hits(player)` |
| 自机判定点 vs 敌机**机体** | **全量比较**（每帧一次，敌机也就几十架） | `EnemyField.touches(player)` |
| 自机子弹 vs 敌机 | **按 y 坐标分桶粗筛** | `game/collision.py` |

分桶省的是**子弹那一侧**的成本：敌机通常只有几架，而自机子弹每帧几百发，
逐发扫一遍全部敌机是 O(弹 × 敌)。把敌机按 y 排好序之后，每发子弹只需要比较 y 邻近的
那几架——`|dy|` 超过「子弹半径 + 最大敌机半径」的敌机不可能相交。

它是**纯性能措施**，唯一要守的性质是「不改变结果」，所以测试拿它和朴素的全量比较
**逐一对照**（随机造一批敌机与子弹，两边的血量分布与去留必须完全相同）。另有两条测试
把窗口的两侧边界钉住：只测一端的话，「窗口上界没生效」这种退化会从列表末端溜过去。

子弹**不穿透**（打中一发就消失）：穿透会让一条弹道在敌机排队飞来时打出成倍的伤害，
而伤害值是按单发调的。规格未规定，本项目定的。

### 敌机身上有两个半径

| 字段 | 来源 | 给谁用 | 大小 |
|------|------|--------|------|
| `Enemy.radius` | 关卡数据的 `hitboxRadius` | 自机子弹**打中**它 | **比贴图还大**（妖精半宽 12、数据给 15） |
| `Enemy.bodyRadius` | 贴图内切圆 × `ENEMY_BODY_RADIUS_FACTOR` | 自机**撞上**它 | **比贴图略小**（弹刺球 16.4 → 12.8） |

两个方向是相反的，而且是有意的：**被弹判定要「打得到」，撞机判定要「没真碰到就不算死」**。
合成一个的话必然有一边是错的——数据那份比贴图大，拿来判撞机就成了「判定圈比眼睛看到的还大」，
这是最招人骂的一类判定。

「略小」不是拍脑袋：弹刺球贴图 32×32、可见半径约 16.4px，系数 0.8 给出 12.8px，
于是撞死发生在自机判定点与球心相距 12.8 + 2 = 14.8px 处——那一刻自机立绘的边缘
离球心只有 2.3px，画面上两人**明显叠在一起**，而死得合理；反过来，贴图最外圈
那 3.6px 是白送的宽容度。

内切圆取的是**短边**（`min(宽, 高)`）：妖精贴图 24×19，取半宽 12 的话自机在它正上方
还差 2.5px 才碰到就会死。这条有专门的测试盯着。

相切不算碰撞这条约定只有一处实现（`circlesOverlap`）：`Collider.checkCollision` 与
`Enemy.touches` 传的是不同的半径，但边界规则必须一致，写在两处迟早只改一边。

`clear_on_death`（关卡里 4 个精英敌人的「被打死时清弹」）在这个模块里接上。
判据必须是「**被打死**」而不是「退场」：`isFinished()` 两者都包含，写成它就会让精英
敌人飞出场时替玩家清掉一屏弹——白送一个大便宜。

### HUD：`ui/` 这一层

HUD（`ui/hud.py`）填的是游戏区右侧那条 224px 的深色带。README 的结构图里早就写着
`ui/ # 界面：HUD、菜单、结算`，本轮把它建了出来。

**它只接收裸值**（`drawHud(canvas, lives, bombs, power)`），不 import `game/` 里的任何
实体类型。这样它既守住了分层，也能脱离自机单独测试——造三个数就能画一帧。

字体是 `assets/fonts/DFPPOPCorn-W12.ttf`，**只加载一次**（2.8MB，每帧读一遍会明显掉帧）。
缓存是有对价的：字体对象绑在 font 模块的初始化状态上，`pygame.quit()` 之后再渲染会抛
`Invalid font (font module quit since font created)`，而缓存恰好让这个失效的对象活过了
quit——所以 `main()` 在 `pygame.quit()` 之前调用 `hud.releaseCaches()`。不缓存反而看不
出这个问题。

**这个字体缺字缺得厉害，而且缺的都是简体字**：它是个日文同人字体，实测缺「弹」
（U+5F39）、「恶」（U+6076）、「测」「试」，但日文写法（弾 / 悪）都在。缺字时 pygame
画的是一个统一的方框——**不报错、也不返回空**，只是画错了，所以「代码看不出来、
肉眼一眼看得出」。踩过两次：HUD 的「炸弹」渲染成「炸」加方框（改用「雷」），
BOSS 名「小恶魔」渲染成「小 魔」（改用原作的「小悪魔」）。

规矩因此是：**任何要显示的文字（包括关卡数据里的名字）都要过一遍 `hud.hasGlyph`**。
界面上的固定标签有 `tests/ui/testHud.py` 逐字守着，数据驱动的文字（BOSS 名）由
`tests/ui/testBossBar.py` 拿真实关卡数据守——静态检查覆盖不到它们。

## BOSS：脚本驱动的敌机

规格 §6.7 把 BOSS 定成**本项目最大的新增模块**（「参考项目完全没有任何 BOSS」），
而写法是规格自己钉的：**生成器协程**。本轮只做了中 BOSS（规格对它的定义是
「道中出现的简化版，通常无符卡，血条短」），所以没有符卡宣言、没有分段血条。

### `Boss` 继承 `Enemy`，住进 `EnemyField.active`

BOSS 与敌机**在引擎眼里是同一种东西**：有血量、有判定圈、被自机子弹打、撞死自机、
死了要离场。继承之后这五条路径全部复用——`collision.py` **一行都没改**，撞机判定、
`clearOnDeath` 清屏、y 分桶、绘制照常生效。另起一个 `BossField` 等于把它们各写一遍。

两者的差别只有两处，都在 `Boss` 里覆盖：

| | `Enemy` | `Boss` |
|---|---|---|
| 怎么动 | 沿样条轨迹（`u += uPerFrame`） | 脚本驱动（`moveTo` / `wait`） |
| 怎么开火 | 查时刻表（`dueAttacks`） | 开火计划（`fires`） |

构造时合成一个**退化的 `EnemySpawn`**（单点路径、`durationFrames=1`、占位血量 1）
喂给父类，于是继承来的 `hasLeft()` 恒为假（`u` 永远是 0），`isFinished()` 只剩
「死了」与「脚本跑完」两条。**占位血量必须是正数**：`isDead()` 是一上来就为真的话，
BOSS 会在出生那一帧被当成死掉的回收掉。

### 脚本：移动走 yield，开火走计划

```python
def midbossScript(boss: Boss) -> Iterator[None]:
    yield from boss.runPhase(MIDBOSS_HP, patrol(boss))


def patrol(boss: Boss) -> Iterator[None]:
    while True:
        boss.stopFiring()
        boss.fires("spread")  # 后台：登记一条开火计划
        yield from boss.moveTo(CENTER, frames=90)  # 前台：边挪边打
        yield from boss.wait(150)
        ...
```

**这条分工不是风格问题**：`yield from` 是顺序的，`yield from boss.fires(...)` 会把
控制权一直交给它直到它返回——那样 BOSS 就没法边挪边打，而边挪边打正是 BOSS 的常态。
所以只有「每帧进一步」的动作（`moveTo` / `wait`）是生成器，开火是**登记一条后台计划**，
由 `Boss.update` 每帧推一拍。

**一帧恰好推进一步**：`update()` 每帧只 `next()` 一次脚本，`yield from` 把这一步透传
到最内层，中间所有层一起挂起。中间层若写成 `while True: next(script); yield` 就会每帧
多吃一步——不报错，只是整个 BOSS 的节奏快一倍，画面上很难看出来，所以有专门的测试。

脚本跑完**不再 `next`**：已耗尽的生成器每次都重新抛 `StopIteration`，在普通函数里它会
一路冒到 `Game.update` 把游戏打崩（PEP 479 只保护生成器内部）。

### 开火计划不走脚本的 yield

`fires(name)` 登记一条计划，计划按**参数自带的** `intervalFrames` 反复打，
`volleyIndex` 从 0 起逐发自增（`wide_ring` 的螺旋靠它，错了就错位）。每帧该打的齐射
由计划排进 `pending`，`dueAttacks()` 返回并清空它——**复用的就是敌机那条通道**，
于是 `EnemyField.fire()` 原样可用：自机狙的角度按本帧的自机位置算、`rng` 是注入的。
脚本里因此**看不到子弹场、自机、随机数**，随机弹幕仍然是「同一份输入同一场战斗」。

另一条通道是 `fireOnce(name, volleyIndex=0)`：**打一发就走**，不登记计划。它存在的
理由是「逐环换朝向」——环形弹的整体旋转是 `volleyIndex × deltaAngleDeg`，而计划里的
volleyIndex 只会自增，没法在中间改方向。所以「左右交替旋转的环」只能一环一环地打：
脚本累加*步数*（+1、0、+1、0……），角度由数据里的 `deltaAngleDeg` 乘出来——
调手感改数据就够了。小恶魔的最终弹幕就是这么写的（`stage/level1.py`）。

`runPhase(hp, script)` 进段时**撤掉上一段的计划**，血归零就结束这一段（判据在推进
之前，血一空就不再出弹）。子脚本写无限循环就行——段的结束由玩家的输出决定，这与
原作一致。

### 立绘：程序化占位图形

规格要求 BOSS 立绘用**程序化绘制的占位图形**（「将来替换为真实美术时逻辑代码零改动」）。
`bakeBossSprite(color)` 画一个带光晕的正五边形、绕中心转 8 个角度烘成一张横向表。
选五边形是因为 45° 的步长下它每帧都不重样——八边形 45° 正好自重复，转起来看不出动。

**帧是烘出来的，不走 `getRotated`**：那个缓存是每张表一份、键里含帧号，大尺寸立绘转
一圈的内存上界正是「性能」一节里点名最贵的一档。

**两个半径都由机体算，不由贴图推**（`radius` = 外接圆，`bodyRadius` = 再乘 0.8）：
`Enemy` 那套「贴图内切圆 × 系数」是给贴图就是机体的敌机用的，而 BOSS 贴图外圈是
**透明光晕**——照那样算，撞机半径会比「打得中」的半径还大，玩家离着十几像素就被撞死。

### 战场数据的挂载点

规格 §7.2 的分工：**JSON 管「何时出 BOSS」与「打什么弹」，代码管「BOSS 怎么打」**。

- `atFrame` / `startPosition`：出场时刻与出场点（写在游戏区上方，脚本第一条 `moveTo`
  把它带进场）
- `attacks`：名字 → 齐射定义。参数走与敌机**同一套** `_extractAttack`，所以子弹规格
  仍由 `_Caches` 共享（同一张贴图只有一份 SpriteSheet），格式错了是加载时报错带位置。
  **脚本里现写子弹规格会绕开这两条**，所以攻击参数不放脚本。
- `script`：点分路径（`touhou.game.stage.level1.midbossScript`），加载器动态 import
  ——规格点名这条路。src/ 里别处没有动态 import（模板层用的是静态注册表），
  两条路各有各的道理：模板是「数据组合出弹幕」，脚本是「一整个 BOSS 的行为」，
  后者本来就该是一个能随便写的 Python 文件。代价是脚本里的语法错误会让**关卡加载
  不出来**（而不是打到一半才炸）——这是有意的，脚本是关卡内容的一部分。
- **血量不在数据里**：它在脚本的 `runPhase(hp=...)`，两处都写必然对不上。血条在
  `maxHp` 为 0（脚本还没进第一段）时不画。

### 血条与离场

`ui/bossBar.py` 画在游戏区顶部（规格 §6.7「段数显示于屏幕顶部」），只收裸值，与 HUD
同一套路。一条血条画的是**本段**的血，下面的小格子是总段数与当前段号。

离场有两条路：**被打死**（清屏——`clearOnDeath` 走的是碰撞模块里那条现成的路，
BOSS 倒下清屏是原作的规矩）与**脚本跑完**（退场，**不清弹**，与「飞走的敌人不掉东西」
是同一条区分）。只有被打死的那条会放爆炸特效，`main` 观察 `enemyField.boss` 从有到无
——注意它可能死在两步中的任何一步（容器回收 / 子弹结算），所以引用要在两步之前留好，
位置也从那份引用上取。

## 关卡数据格式

`assets/levels/level_1.json` 是本项目自己的格式，由 `tools/migrateLevel.py`
从参考项目的旧格式一次性转换而来（旧内容留在 git 历史里）。

```
meta  : name / durationFrames
waves : [{ atFrame, spawns: [...] }]
spawn : atFrame / startPosition / trajectory / durationFrames
        / sprite{path, frameSize, frameCount} / hitboxRadius / hp
        / attacks / drop / clearBulletsOnDeath
attack: { pattern, startFrame, params{ bullet, ... } }
bullet: { path, frameSize, frameCount, hitboxRadius, rotatesToVelocity? }
bosses: { 角色名: { atFrame / startPosition / name / color / segments
                    / attacks{ 名字: attack } / script } }
```

`bosses` **没有 `startFrame`**：BOSS 的开火时机由脚本决定，不该再叠一层时刻表。
血量也不在这里（在脚本的 `runPhase` 里），见「BOSS」一节。

BOSS 的攻击参数里 `coneCount` / `ringCount` / `burstCount` 是**过校验用的**（它们是
参数类的必填字段）——BOSS 是持续开火，打到本段血光为止，不看「打几波」那个数。

旧格式的硬伤（位置参数数组靠数位读、单位混用、贴图尺寸重复声明）在这里都消失了。
`tools/migrateLevel.py` 的模块文档记着迁移时要处理的四个陷阱。

### 两种帧，别混

- `waves[].atFrame` 与 `spawns[].atFrame` 是**关卡绝对帧**
- `attacks[].startFrame` 是**相对该敌人出生**的帧数——攻击的时刻本来就跟着敌人
  自己的时间轴走（旧格式里它用的是敌人轨迹参数 `u`）

「出生后第 N 帧开火」严格等于「出生帧 + N」，包括 N = 0。为此 `EnemyField.update`
把**出生放在推进之后**：否则刚出场的敌机会凭空老一帧，所有弹幕都早 1/60 秒。

### `waves` 只是个可读性分组

**每个 spawn 自带权威的 `atFrame`**；波上的 `atFrame` 只等于本波最早的那个，
让关卡读起来像「第 N 帧刷第一波」。校验会断言这一致性，但运行期只信 spawn 自己的。

为什么不让波内共用时刻：同一波里的出生时刻本来就是错开的（例如 50.0、50.1、
50.4…52.5 秒），压成同一个时刻会让敌机整波同时出现——那是迁移改变了语义，
而迁移只该改变表达。

### 单位

- **`speed` 是像素/帧**（本项目引擎统一用像素/帧）。旧格式是像素/秒，
  迁移时除以 60——**漏掉这一步不会报错**，只是子弹以 150 像素/帧飞出去、
  三帧横穿游戏区然后被回收，画面上表现为「敌机在开火但场上几乎没有子弹」。
- `intervalFrames` **可以是小数**。旧格式的时间是轨迹参数 `u`，除以敌机速度后
  未必落在整数帧上（例如 `0.06 / 1 × 60 = 3.6`）。取整会让每个间隔都偏一点，
  累积起来可观，所以保留小数——「迁移只该改变表达」这条优先于「帧是整数」的直觉。

### `durationFrames` 覆盖整条路径（与规格公式差一段）

我们的路径是 `[startPosition] + trajectory`，比 `trajectory` 多一段，所以：

```
durationFrames = len(trajectory) / speed × 60        # 我们的写法
durationFrames = (len(trajectory) - 1) / speed × 60  # 规格的公式，它假定路径只有 trajectory
```

照规格的公式算会让每架敌机比预期早走完一段，也就是快 `len/(len-1)` 倍
（4 点轨迹快 33%）。**每段的像素速度不变**，只是总时长多一段。
`tests/game/testLevelData.py` 把 240（而不是 180）这个数钉死了。

## 关卡数据与坐标系

`assets/levels/level_1.json` 描述整关：114 个敌人，每个带出生时刻、轨迹、血量、
贴图、攻击参数与掉落。它来自参考项目，格式与坐标都是那一套。

### 坐标以**游戏区左上角**为原点；换算只缩放、不平移

参考项目的游戏区是 600×700（`GAME_ZONE = 50, 50, 600, 700`），我们的是 384×448，
而 `384/600 == 448/700 == 0.64`——我们的游戏区就是它的 0.64 倍。所以换算只有缩放：

```python
our_x = PLAYFIELD_X + ref_x * 0.64
our_y = PLAYFIELD_Y + ref_y * 0.64
```

**证据是镜像对称。** 关卡照左右镜像设计，114 个出生点里有 72 个能在镜像位置
找到伙伴，而这些镜像对的对称轴**全部恰好是 300.0**——正是 x ∈ [0, 600] 的中心。
若把数据当成窗口绝对坐标（原点在 50），对称轴该是 350，12 对里一对都对不上。
旁证：换算后左右越界量**严格相等**（都是 76.8px），原点若偏了镜像不会保持对称。

不换算的后果是所有敌机在一条放大 1.5625 倍的轨迹上飞、大半时间在画面外——
不崩溃，只是「敌人好像不太对」。

### `time` 是出生时刻，而文件顺序不是出生顺序

`time` 从 7.0 到 56.9 秒，`length` 是 65 秒的关卡时长。文件里的顺序有 8 处逆序，
必须排序。另有 36 组时刻相同的双生出生——用 dict 按时刻去重会静默丢掉每对的一半。

### `speed` 的单位是「样条参数 u / 秒」

**不是**像素/帧，也不是像素/秒。轨迹参数 `u ∈ [0, len(path)-1]`，每经过一个控制点
区间耗时 `1/speed` 秒，敌机存活 `(len(path)-1)/speed` 秒。

两个独立来源一致：本项目规格文档的说明，与参考项目源码里的
`self.t += self.speed * delta_time`。之所以专门写一条，是因为**「`speed` 是像素/帧」
是个看起来很合理的误读**（1 和 2.4 都小得很像像素/帧），读错之后敌机会以蜗牛速度
爬行，而且不报错。

### 轨迹是**均匀三次 B 样条**

控制点**不落在曲线上**——B 样条是逼近型的，曲线落在控制点的凸包内。这一条同时带来
两个好处：**永不越出控制点包围盒**（实测 114 条真实轨迹越界 0.0000px；Catmull-Rom
最大越界 13.6px、21/114 条超 5px），以及转弯天然平滑。特征矩阵见 `core/spline.py`。

**端点用镜像外插**（`2*p[0] - p[1]`），这不是可选的：有了它 u=0 才恰好落在首控制点上，
「敌人从 `start_position` 出发」才是精确成立的。

### 重复的控制点是标准写法，不是笔误

关卡里有 70 组相邻控制点完全相同，最极端的是敌 70/71 整条轨迹 13 个点全同。

- **连写 3 次**（16 条，全是妖精）→ 让曲线**恰好穿过**该点。B 样条否则不经过首控制点，
  连写三次是「从这里开始」的标准写法。
- **连写 12～13 次**（敌 68–71，hp 25/40 的精英）→ **停在原地**。敌 70 就是
  「从右边缘飞进来、移到 x=304、僵持 13 秒」。

所以样条实现里**不需要任何「重复点 = 停住」的特判**。当初误以为要用 Catmull-Rom 时
才需要给重复点打补丁——用错样条才需要补丁。

### 容易踩的数据细节

- **贴图路径自带 `assets/` 前缀**（`["assets","sprites",...]`），而 `assetPath()`
  会自己补一个；直接透传会去找 `assets/assets/sprites/...`。
- **同一张贴图只该有一个 `SpriteSheet`**。旋转缓存是每张表一份，给 114 个敌人各建
  一张表会让「360 × 帧数」的上界乘以 114。
- **敌机判定半径很宽松**，与子弹正相反：妖精贴图 24×19、半宽只有 12，数据给半径
  **15**；弹刺球 32×32、半径 16 正好是外接圆。这是有意的，别「顺手修正」。
- **`collider.offset` 数据里全是 `(0,0)`**，本轮因此没实现偏移。格式里有这个字段——
  将来若有人改数据填了非零值，必须先实现它，否则判定圈错位而没人发现。
- `start_position` 是路径的**第一个点**，不是出生后要瞬移过去的位置：114 个敌人
  没有一个的 `trajectory[0]` 等于它的 `start_position`，而两者间距与该轨迹其余段
  同量级（比值中位数 1.29）。

### 与参考实现的出入（无法核对的那部分）

参考项目的 `Splines.py` **我们没有拿到**（网络受限，本地也没有拷贝）。上面这些结论
来自两处：本项目那份规格文档（随 `docs/` 移出版本控制，可用
`git show 7fbca5f^:docs/superpowers/specs/...` 恢复）里对 `BasisSpline` 的描述，
以及我们自己在 114 条真实轨迹上的实测。**所以样条是我们的选择，不是它的复刻**——
真要说差别，路径形状可能与原作有出入。设计文档已声明本项目不是逐帧还原。

### 缩放规则：**只有关卡几何缩放**，其余一律保持原值

这条规则要说清楚，因为它看起来不自洽，但每一条都有理由：

| 量 | 缩放？ | 理由 |
|----|--------|------|
| 敌人的路径坐标 | **× 0.64** | 必须缩放，否则整关跑到画面外 |
| 弹速 | 否（只做 px/秒 → px/帧） | 「角色尺度」的量 |
| 判定半径（敌人与子弹） | 否 | 同上，而且它是手感调参量 |
| 随机中心的偏移 | 否 | 同上 |
| 精灵尺寸 | 否（按原图绘制） | 美术素材就是这个大小 |

**理由是「相对关系」**：位置必须缩放才能装进我们的屏幕；而速度、半径、精灵尺寸
之间的比例决定了手感与观感，同比例保留才对。若只缩放位置而把速度也乘 0.64，
玩家相对子弹就会快 1.5625 倍、躲避比原作宽松——所以速度**不**缩放。
（`constants.py` 里队友定的 `PLAYER_SPEED_NORMAL = 370 / 60`、`ITEM_HOMING_SPEED = 500 / 60`
也是这么处理的：只做 px/秒 → px/帧，不乘 0.64。）

判定半径是这条规则里**最不确定**的一项，属于「实证之后才调」的数值。它现在已经
真的参与判定了（自机子弹打敌机的碰撞），但只在「打没打中」这一个地方起作用——
手感是否合适还没被实测过。

### 关卡文件已经迁移到新格式

`assets/levels/level_1.json` 现在是本项目自己的格式（详见「关卡数据格式」），
坐标**已经是本项目游戏区的坐标**，加载器不再做任何换算。
上面那个 0.64 变换现在只活在 `tools/migrateLevel.py` 里——它是一次性迁移工具，
换完就不再有别的调用方。

## 性能：按角度预旋转缓存

**这是本项目最重要的性能设计。**

参考项目在每发子弹的构造函数里，对子弹 sprite sheet 的**每一帧**都调用 `pygame.transform.rotate`。弹幕密集时每秒生成数百发子弹、每发旋转好几帧——这一行单独就能吃掉全部帧预算。这不是微优化，是 60fps 和幻灯片的分界线。

本项目的做法是把旋转结果按 `(帧序号, 整数角度)` 缓存起来（`core/spriteSheet.py`）。角度归一到 `[0, 360)` 的整数度后只有 360 种取值，所以缓存是**有界**的；而且是**按需生成**的——只有实际用到的角度才会被创建。

**内存量级**：缓存条目上限是 `360 × 帧数`，但**每个条目的字节数不一样**：45° 的旋转结果外接矩形最大。实测 16×16 的贴图转到 45° 是 22×22，24×24 的变成 33×33，也就是**约 4 倍像素**。所以按「1440 个 16×16 surface ≈ 1.5 MB」估算偏乐观，最坏情况接近 3 MB（4 帧 16×16 的子弹表）；自机立绘若真的用遍所有角度，约 14 MB。条目数有界、按需生成，结论不变，但假设要写清楚。

还有一处相关的取舍：**不是所有子弹都该旋转**（见「子弹与弹幕场」一节）。圆球弹旋不旋转外观完全一样，而实测 `getRotated(帧, 0)` 与 `getFrame(帧)` **不是同一个对象**——0° 旋转也会另存一份。所以 `BulletSpec.rotatesToVelocity` 为假的弹走 `getFrame`，省下的是 360 个缓存条目而不只是 CPU。

其余措施：

- 子弹对象用对象池 + `__slots__`（已实现，见「子弹与弹幕场」）
- 己方子弹 vs 敌机的碰撞按 y 坐标粗筛（**仍待实现**，它服务的是另一条碰撞路径）

**明确不做**：空间网格、numpy 向量化、多进程。这些都是"实测证明需要"之后才上的手段，提前上只会让代码变难读。

### 为什么启动是 `python run.py` 而不是 `python -m touhou`

`python -m touhou` 要求 `touhou` 这个包能被 import，而这在源码树里**默认不成立**
——包在 `src/` 下（src-layout，见 `pyproject.toml` 的 `package-dir`）。三种绕法
各有各的代价：

| 写法 | 问题 |
|------|------|
| `pip install -e .` | 要有 pip、要先建环境；而且它把包装进了**某个具体的解释器**，换台机器得再来一遍 |
| `PYTHONPATH=src python -m touhou` | 只在 POSIX 上成立：Windows cmd 要写 `set PYTHONPATH=src`，PowerShell 又是 `$env:PYTHONPATH="src"`。**没有一条三平台通用的写法** |
| `pip install .`（非 editable） | **装得上但跑不起来**（实测）：包装进 site-packages 后，`core/paths.py` 那套「从本文件往上数三级找项目根」的算法指向 site-packages 的父目录，而 `assets/` 既不在那儿、也没被打进 wheel |

所以启动做成一个**仓库根目录下的脚本**：把它自己所在目录的 `src/` 挂进
`sys.path` 再调 `touhou.main`。全部路径由 `__file__` 推出，没有一处写死的绝对
路径，因此拷贝到哪台机器、从哪个目录调用都一样。

三个附带的决定：

- **报错的顺序是刻意的**：先查解释器版本、再查 `src/` 与 `assets/` 在不在、再查
  依赖装没装，**最后**才 import 游戏。反过来写的话，一台机器上装着好几个 Python
  时，玩家最先看到的会是 `ModuleNotFoundError: pygame`，而真正的原因可能是
  「你这个 python 是 3.8」。
- **不自动装依赖**：缺 pygame 时只打印该跑哪条命令。往别人的解释器里装包是件
  该由他自己点头的事（他也可能想装官方 `pygame` 而不是 `pygame-ce`）。
- **最低版本写了两份**（`pyproject.toml` 的 `requires-python` 与 `run.py` 的
  `MINIMUM_PYTHON`）：它们给不同的人看——那个给 pip 看（决定装不装得上），
  这个给玩家看（决定报不报错）。`tests/testRun.py` 有一条测试比对两处。

这些承诺（三平台通用、不写死路径、报错说人话）全都**不是「跑起来才对」的那种**
——错了游戏照样能玩，只有在别人的机器上才炸，而那时作者不在场。所以
`tests/testRun.py` 逐条守着它们。

### 为什么不使用 numpy

参考项目用 numpy 表示二维向量：`Vector2` 内部就是一个 `np.array([x, y])`。本项目改成纯 Python 的两个浮点数。

原因是 **numpy 对小数组的单次运算其实比纯 Python 慢**。`np.array([x, y])` 每次都要构造一个数组对象，这个开销远大于它省下的那两次浮点加法。而弹幕引擎每帧要做几万次向量加法、归一化、旋转——在这种场景下，numpy 是纯粹的负收益。

numpy 真正有价值的场景是**批量数组运算**：一次对几千个数字做同样的操作。如果将来弹幕数量涨到需要向量化处理（比如把全部子弹位置存成平行的数组，一次性更新），那时会重新引入它。在那之前，纯 Python 更简单也更快。

## 参考项目与已修正的缺陷

本项目的素材、关卡数据格式以及若干实现思路来自 [NumPix/pygame-touhou](https://github.com/NumPix/pygame-touhou)（MIT，Copyright 2023 Leonid Ushakov）。**复用时不能照搬它的全部实现**——它有几处真实缺陷，本项目已修正：

**一、碰撞判定公式在数学上是错的**

它写的是：

```python
((a.position - b.position) * (a.position - b.position)).length() < (a.radius + b.radius) ** 2
```

它的 `Vector2.__mul__` 对两个向量做**逐分量乘法**，得到 `[dx², dy²]`，再取 `.length()` 就是 `sqrt(dx⁴ + dy⁴)`——既不是距离也不是距离平方。两边量纲对不上，判定边界根本不是一个圆。

后果可以算出来：**沿坐标轴时它退化成正确的 `d < r₁+r₂`，但在 45° 方向上放宽到 `d < 2^(1/4)·(r₁+r₂) ≈ 1.19·(r₁+r₂)`**——判定区是个圆角方形，斜向命中比看起来多出约 19%。这种「跑得起来、只是偏」的偏差正是本文件反复强调要防的那一类。

正确写法是比较 `dx² + dy²` 与 `(r1+r2)²`。回归测试在 `tests/core/testCollider.py`。

**二、旋转方向相反**

见上文「关键接口约定」的移植警告。已按其源码核对：它的 `Vector2.rotate` 是
`np.matmul(self.coords, rotor)`，行向量乘矩阵，等价于旋转负角度。

**三、每发子弹重复创建旋转贴图**

见上文「性能」一节。它的 `Bullet.__init__` 对 sprite sheet 的每一帧都调用一次
`pygame.transform.rotate`，而且是**每发子弹**都做一遍。

**四、没有对象池，也没有 `__slots__`**

子弹是每发新分配、带 `__dict__` 的普通对象。本项目在 `game/bulletField.py` 里
补上了对象池与 `__slots__`（见「子弹与弹幕场」）。

另外两处顺带避开的坑，记在这里以免有人从那边抄回来：

- 它回收子弹时**一边遍历一边 `remove()`**，于是紧跟在被删元素之后的那颗弹，
  当帧会被整个跳过——既不移动也不做碰撞判定。本项目用倒序 + 交换删除
  （见「子弹与弹幕场」）。
- 它的子弹帧动画是**死代码**：`next_sprite()` 从未被调用，而且真调用会崩
  （`self.sprite_sheet` 在 `__init__` 里已被换成 `list`，却去访问 `.length`）。
  所以那边的子弹实际是静态图。移植动画时不要参考它。

## 代码约定

### 命名

| 类别 | 风格 | 示例 |
|------|------|------|
| 类名 | `PascalCase` | `SpriteSheet` |
| 函数/方法/变量/参数 | `lowerCamelCase` | `getRotated`、`angleDeg` |
| 模块级常量 | `UPPER_SNAKE_CASE` | `FPS` |
| 文件名 | 与其中主要类名一致 | `spriteSheet.py` |

这套风格与 PEP 8 的函数命名建议不一致，因此 ruff 关闭了对应检查（`N802`/`N803`/`N815`/`N999`）。

### 定义类的模块以 `from __future__ import annotations` 开头

`src/touhou/` 下任何定义了类的模块都以此行开头。理由是方法签名引用自身所在的类（`def __add__(self, other: Vector2) -> Vector2`）时，Python 3.13 及更早版本会在类体执行时**立即求值**注解，此时类名尚未绑定，直接 `NameError`；延迟求值要到 3.14 才默认启用。

**这个 import 看起来没用，但删掉就会在导入阶段崩溃**，所以每处都写了注释说明。

### 注释解释「为什么」

代码和文档是写给**人**读的。注释要解释为什么这么写，而不是复述代码在做什么——`# 把 x 加一` 这种注释不如没有。函数名和变量名要能自解释，宁可长一点也别用 `d`、`tmp`、`data2`。

这不是审美偏好。弹幕游戏的代码里有大量数学，半年后回来看时唯一能依靠的就是命名和注释。

### 借鉴不等于抄袭

实现功能前先找现成方案，但**注意对方的开源协议**。没有 LICENSE 的项目意味着"保留所有权利"，可以读它的设计思路，但不要复制代码。
